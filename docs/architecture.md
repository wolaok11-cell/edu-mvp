# 系统架构说明

## 1. 目标

平台采用“链下体验优先，链上关键状态可信”的半去中心化模式。用户不需要理解钱包、Gas 和复杂签名流程，平台通过嵌入式钱包、稳定币支付和托管结算完成核心信任闭环。

## 2. 服务拆分

### `apps/web`

面向学生、家长、教师的前台产品，负责：

- 首页、教师广场、教师详情页
- 下单、支付、订单详情、评价
- 学生中心和教师工作台
- 钱包接入和交易状态提示

### `apps/admin`

面向平台运营和仲裁员，负责：

- 教师审核
- 订单总览
- 争议裁决
- 财务统计
- 推荐位和风控配置

### `apps/api`

统一业务后端，负责：

- 账号体系、角色切换、资料编辑
- 教师资料、课程产品、可预约时段
- 订单创建与状态流转
- 支付参数生成与 tx 上报
- 争议管理、评价、通知
- 链上事件回写和可验证记录映射

### `watcher / worker`

建议独立为后台任务服务，负责：

- 监听合约事件
- 校验区块确认数
- 幂等写入数据库
- 更新订单状态
- 触发通知
- 触发信誉记录或 attestation 签发

## 3. 关键模块边界

### 链上负责

- 订单托管资金
- 订单关键状态
- 自动放款 / 退款执行
- 争议冻结与裁决执行入口
- 事实型信誉事件

### 链下负责

- 用户登录与资料
- 搜索、筛选、排序
- 课程详情与富文本信息
- 评价文本与标签
- 争议证据正文与附件
- 消息通知和后台审计

## 4. 订单状态流

```text
pending_payment
  -> escrowed
  -> scheduled
  -> tutor_marked_complete
  -> completed

escrowed / scheduled
  -> disputed
  -> refunded
  -> cancelled
```

链上状态建议和数据库状态不强制一一对应，但必须在 watcher 层维护稳定映射。

## 5. 建议模块划分

### API 模块

- `auth`
- `users`
- `tutors`
- `lesson-products`
- `orders`
- `payments`
- `reviews`
- `disputes`
- `notifications`
- `admin`
- `webhooks`

### 数据库读写关注点

- `orders` 和 `order_status_logs` 是主状态源
- `payments` 保留交易轨迹
- `chain_event_receipts` 做事件幂等
- `attestation_records` 维护链上和业务对象映射
- `admin_operation_logs` 用于后台审计

## 6. 推荐落地顺序

### 第一阶段

- 建表
- 搭 API 路由
- 跑通订单创建、支付参数生成、tx 上报

### 第二阶段

- 跑通完课确认、自动放款、争议冻结
- 搭 watcher 事件回写
- 前台接入订单状态展示

### 第三阶段

- 完善评价、通知、财务统计
- 上线后台审核和裁决
- 做真实试点教师和真实订单验证

## 7. 风险控制约定

- 管理员权限最小化，关键配置建议多签
- 合约必须支持暂停
- 只开放稳定币白名单
- 涉及未成年人信息时，避免过度采集敏感信息
- 争议证据应存储在具备访问控制的对象存储中
